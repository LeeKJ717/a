# 13장 로컬 언어 모델로 논문 읽기: 표와 서술을 옮겨 적게 하고 환각을 걸러 내는 절차

제1권의 각 장은 논문의 표와 서술을 사람이 읽고 옮겨 적은 것에 기댄다. 그런데 장마다 "원문 쪽 확인 필요"가 남아 있다. 논문 PDF에서 표를 뽑으면 열이 흩어져서 어느 숫자가 어느 칸의 것인지 알 수 없는 경우가 있었고(제1권 11장의 Cui 등 표 1과 Duggan 등 표 3), 어느 쪽 숫자가 맞는지 정하지 못한 채 "미결"로 남긴 항목도 있었다. 논문이 수십 편, 수백 편이 되면 사람이 일일이 원문과 맞춰 보기 어렵다. 그래서 언어 모델(글을 이어 쓰도록 훈련된 신경망)에게 표와 서술을 옮겨 적게 하는 방법을 생각해 볼 수 있다. 인터넷의 서비스에 원고를 보내지 않고 자기 컴퓨터에서 돌리는 모델이 "로컬 언어 모델"이다.

그러나 언어 모델은 원문에 없는 숫자나 문장을 그럴듯하게 지어내는 일이 있다고 알려져 있다. 이것을 흔히 환각이라 한다. 논문의 숫자를 다루는 일에서 환각은 치명적이다. 그래서 이 장의 중심은 모델을 쓰는 법이 아니라, 모델이 낸 결과를 원문과 대조해 환각을 걸러 내는 절차이다.

이 책이 이 장을 쓴 컨테이너에는 GPU가 없고, 메모리는 8 GiB(실제로 쓸 수 있는 양은 약 6.5 GiB), 코어는 2개이다. 이 장을 쓰기 전에 가장 먼저 한 일은 이 환경에서 로컬 언어 모델을 실제로 실행할 수 있는가를 시험한 것이다. 결과는 다음과 같다. **모델을 실행하지 못했다.** CPU로 모델을 돌리는 라이브러리(llama-cpp-python)는 설치되고 불러졌지만, 모델 가중치를 내려받을 곳이 막혀 있었고 GitHub와 PyPI에서도 가중치를 얻지 못했다(13.2절). 그러므로 이 장에는 **언어 모델이 낸 출력이 하나도 없다.** 이 책은 모델이 어떤 값을 냈을 것이라고 상상해서 적지 않았다.

대신 이 장은 모델 없이도 실제로 실행되는 두 가지를 만들었다. 하나는 모델이 낸 인용, 숫자, 표를 원문과 맞춰 보는 환각 점검기(`halluccheck-v1.py`)이다. 다른 하나는 모델 서버(Ollama)를 부르는 코드(`llm-client-v1.py`)인데, 이것은 문법 검사와 실패 경로까지만 실행했고 "z840 실행 필요"로 표시했다. 점검기는 (가) 이 책이 모델이 틀리게 쓸 법한 값을 일부러 섞어 만든 시연 출력과, (나) 제1권 11장의 장부와 본문에 실행했다. 시연 출력은 모델이 쓴 것이 아니라는 점을 몇 번이고 밝힌다.

**이 장이 하지 않는 것.**

- 이 장은 언어 모델을 한 번도 실행하지 못했다. 모델이 표를 얼마나 정확히 옮기는지, 환각을 얼마나 내는지, 어떤 모델이 좋은지에 대한 측정값이 이 장에는 없다.
- 이 장의 "모델 출력"은 모두 이 책이 직접 쓴 시연값이다. 시연값으로 점검기가 심은 오류를 찾는다는 것을 보였을 뿐, 실제 모델의 환각을 점검기가 얼마나 잡아내는지는 측정하지 못했다.
- Ollama 서버를 부르는 코드(13.10절)의 응답 해석 부분은 한 번도 실행하지 못했다. 응답의 모양은 공식 문서에서 확인하지 못했고 제3자의 글에서 읽은 것을 바탕으로 썼다.
- 모델의 라이선스와 로컬 실행 사양은 공식 페이지를 읽은 것만 적는다. 읽지 못한 것은 "확인 필요"이다(13.3절).
- 이 장은 논문 PDF에서 글자와 표를 뽑는 단계(2장)를 다시 하지 않았다. 이 장의 "원문"은 제1권 11장의 원고이며, 제1권이 논문에서 옮겨 적은 글이다. 논문 자체가 아니다. 제1권의 옮겨 적기가 틀렸다면 점검기는 그 틀림을 원문으로 받아들인다.
- 점검기는 글자와 산술만 본다. 뜻의 오류를 찾지 못한다(13.6절).

**이 장에서 확인한 일곱 가지.**

1. `pip install llama-cpp-python`은 성공했다(0.3.36, 이 컨테이너에서 소스를 빌드해 6분 41초). `import llama_cpp`도 성공했다. 설치가 되었다는 것은 모델이 돌아간다는 뜻이 아니었다.
2. 모델 가중치를 두는 사이트(Hugging Face, hf-mirror, ModelScope, Ollama의 사이트와 저장소)는 이 컨테이너에서 접속되지 않았다. GitHub의 `raw.githubusercontent.com`과 PyPI는 접속되었으나, llama.cpp 저장소 안의 gguf 파일은 어휘 파일뿐이었고 PyPI 이름 25개에서 가중치를 담은 패키지를 찾지 못했다.
3. 어휘만 든 gguf 파일은 불러졌으나(어휘 크기 32000) 글을 생성하려 하자 `AssertionError: Memory is not initialized`로 실패했다. 가중치 없이는 한 글자도 생성하지 못한다.
4. 점검기의 단위 시험 40개가 모두 통과했다. 시험을 만들고 돌리는 과정에서 점검기의 오류를 이미 한 개 잡았다(정수 표의 합에 ±1을 허용하던 오류).
5. 시연 출력(심은 오류 14개, 원문 결함의 충실한 옮김 2개, 정상 줄 16개)에서 점검기는 찾도록 설계한 오류 10개를 모두 지적했고, 설계상 못 찾는 오류 4개는 하나도 지적하지 못했으며, 정상 줄 16개에는 지적이 없었다. 처음 실행에서는 정상 줄 2개를 잘못 지적했고(표 행 합의 우연한 일치) 이를 고친 뒤의 결과이다.
6. 제1권 11장의 장부에서 제1권이 "미결"로 적은 어긋남 11개 가운데 점검기는 2개(본문의 23 = 21 + 5, 에벤키 C3c1 56.6%의 n = 127)를 지적했고 9개는 지적하지 못했다. 제1권이 지적하지 않은 백분율 2개(58.8%, n = 176과 50.7%, n = 285)가 그 표본 수에서 만들어질 수 없다는 새 후보를 냈다. 이 둘이 논문의 오류인지는 확인하지 못했다.
7. 제1권의 숫자와 어긋난 값은 없다. 제1권 원고의 어느 값도 이 장에서 바뀌지 않았다. 새로 지적된 것은 제1권이 이미 쓴 값에 대한 후보이다.

## 13.2 이 컨테이너에서 모델을 돌릴 수 있었는가

이 절은 시도한 것을 시도한 순서대로, 성공과 실패를 그대로 적는다. 환경은 다음과 같다. 리눅스 컨테이너(커널 6.18), 코어 2개, 메모리 8,027 MiB(그 가운데 쓸 수 있는 양 6,669 MiB), GPU 없음, 파이썬 3.13.16, C 컴파일러와 cmake가 있다(`env-check.log`). 네트워크는 패키지 저장소(PyPI)와 GitHub의 일부만 열려 있다.

<div class="method" markdown="1">

#### 실습 13-1. CPU 추론 라이브러리 llama-cpp-python의 설치와 불러오기

**입력.** 없음. 새 가상환경에 설치했다.

**명령.**

```
$ python3 -m venv venv13
$ venv13/bin/pip install llama-cpp-python
$ venv13/bin/python -I -c "import llama_cpp; print(llama_cpp.__version__)"
```

**결과(`install-llamacpp.log`, `import-llamacpp.log`).** 설치에 성공했다. 휠(파이썬 설치 파일)이 미리 만들어져 있지 않아 이 컨테이너에서 소스로부터 빌드했고, 실제 걸린 시간은 6분 41초(사용자 CPU 시간 8분 4.7초)였다. 만들어진 휠은 25,286,354 바이트이다. 함께 설치된 것은 numpy 2.5.4, jinja2 3.1.6, MarkupSafe 3.0.4, diskcache 5.6.3, typing_extensions 4.16.0이다. `import llama_cpp`는 성공했고 버전은 0.3.36이었다.

**확인.** CPU 추론 도구의 설치는 가능하다. 다만 6분 41초가 걸렸고, 이 시간은 컴퓨터의 코어 수에 따라 달라진다. 빌드 옵션(CPU 명령어 확장을 쓰는지 등)은 이 책이 로그에서 확인하지 않았다.

#### 실습 13-3. GitHub와 PyPI에서 가중치를 얻을 수 있는가

**입력.** 접속되는 두 곳(GitHub의 raw 파일, PyPI)에서 가중치를 담은 파일을 찾는다.

**명령과 결과.**

(가) GitHub 저장소 검색. 설치된 `gh` 명령으로 "tinystories gguf" 저장소 검색과 파일 확장자 `gguf` 코드 검색을 시도했다(`github-model-search.log`). 토큰이 유효하지 않다는 안내가 나왔고, 두 검색 모두 HTTP 403 "이 GitHub API 경로는 쓸 수 없다. 세션은 설정된 저장소에 묶여 있다. 저장소 범위의 엔드포인트를 쓰라"로 거절되었다. 그러므로 GitHub에서 가중치를 올린 저장소를 검색으로 찾지 못했다. 이 책이 이미 알고 있는 주소가 없어서 더 시도하지 않았다.

(나) llama.cpp 저장소가 가진 gguf 파일. 저장소의 `models` 폴더에 어휘 파일(`ggml-vocab-*.gguf`)이 있는 것으로 알고 있어, raw 주소로 두 개를 내려받았다(`github-raw-gguf-try.log`). `ggml-vocab-llama-spm.gguf`는 723,869 바이트, `ggml-vocab-gpt-2.gguf`는 1,766,807 바이트였고 HTTP 200으로 받아졌다. 이름이 가리키듯 어휘(토큰의 목록)만 든 파일이다. 이 책은 이 파일들의 용도를 저장소 문서에서 확인하지 않았고, 아래 실습 13-4의 실행 결과로 어휘만 들었음을 확인했다.

(다) PyPI. 모델 가중치나 작은 모델을 파일에 담았을 것 같은 패키지 이름 25개를 PyPI의 JSON API로 조회해 최신 릴리스의 최대 파일 크기를 보았다(`pypi-model-probe.log`). 15개가 존재하고 10개는 없었다(예: llamafile, tinystories, stories15m, nanogpt, distilgpt2는 없음). 존재하는 것 가운데 가장 큰 파일은 llama-cpp-python 76.59 MB, gpt4all 121.61 MB였고 나머지는 모두 12 MB 이하였다. 가장 큰 gpt4all의 휠을 내려받아 파일 목록을 열었다(`pypi-gpt4all-wheel-list.log`). 147개 파일 가운데 가장 큰 것은 104,657,616 바이트와 104,495,672 바이트의 CUDA용 공유 라이브러리(`.so`)였고, 확장자가 `.gguf`, `.bin`, `.safetensors`인 파일은 없었다. 나머지 14개 패키지의 파일은 크기만 보았고 내용은 열지 않았다.

**확인.** 이 컨테이너에서 접속되는 곳에서는 모델 가중치를 얻지 못했다. PyPI에 가중치를 올린 작은 모델이 따로 있는지는 이 책이 모른다. 25개 이름은 이 책이 떠올린 것이며 PyPI 전체를 검색한 것이 아니다(PyPI에는 검색 API가 없다).

## 13.4 환각과 점검의 기본 개념

<div class="theory" markdown="1">

#### 이론 배경: 모델은 무엇을 틀리게 옮기는가, 그리고 어느 것을 기계로 점검할 수 있는가

언어 모델에게 "이 원문에서 표를 마크다운으로 옮겨라"고 시키면 모델은 원문을 보고 다음에 올 글자를 예측해 이어 쓴다. 이 과정에서 생길 수 있는 오류를 이 책은 일곱 가지로 나눈다. 이 분류는 이 책이 점검기를 설계하려고 세운 것이며, 어느 모델이 어느 오류를 얼마나 내는지는 측정하지 못했다.

1. **지어낸 인용.** 원문에 없는 문장을 따옴표 안에 쓴다. 원문 문장을 의역해 놓고 따옴표를 붙이는 것도 여기에 든다.
2. **없는 숫자.** 원문에 없는 숫자를 쓴다.
3. **숫자의 변환 오류.** 숫자의 두 자리를 바꾸거나(78을 87로) 소수점 자리를 틀리게(0.00079를 0.0079로) 쓰거나 비율과 백분율을 혼동한다(66.7%를 0.667%로).
4. **단위의 오류.** 값은 맞고 단위가 틀린다(100~200 bp를 100~200 kb로).
5. **표의 구조 오류.** 행이나 열이 합쳐지거나 밀리고, 합계가 맞지 않는다.
6. **범위의 오류.** 확률이 1을 넘거나, 연대 구간의 앞뒤가 바뀐다.
7. **뜻의 오류.** 숫자는 원문에 있으나 엉뚱한 항목에 붙고, 부정문이 뒤집히고, 이름이 바뀐다.

이 가운데 1~6은 **원문과 글자를 맞추거나 산술을 하면** 모델 없이 기계로 점검할 수 있다. 7은 기계로 점검하기 어렵다. 점검기가 맞다고 한 줄도 7의 오류를 품을 수 있다. 그러므로 점검은 **기계가 걸러 낼 수 있는 것을 먼저 걸러 내고, 사람이 볼 곳을 줄이는** 순서로 한다. 점검기의 통과가 정확성의 증명이 아니라는 점이 이 장의 가장 중요한 한계이다.

한 가지를 더 구분해야 한다. 점검기가 지적한 줄이 **모델의 오류**일 수도 있고 **원문 자체의 오류**일 수도 있다. 모델이 원문의 어긋난 숫자를 충실히 옮겨도 점검기는 그 줄을 지적한다. 지적은 "문서 안에서 맞지 않는다"는 뜻이지 "모델이 틀렸다"는 뜻이 아니다. 13.6절의 시연에서 이 두 경우를 따로 심었다.

</div>

<div class="theory" markdown="1">

#### 이론 배경: 반올림을 고려한 산술 점검과 백분율의 표본 수 점검

**구간 산술.** 논문의 숫자는 반올림되어 있다. 4.01 + 6.29 + 89.71 = 100.01이라고 쓰여 있고 합이 100.00이라고 적혀 있다면, 이것을 틀렸다고 해서는 안 된다. 각 숫자가 소수 둘째 자리까지 반올림되었다면 원래의 값은 ±0.005의 구간 안에 있다. 점검기는 숫자를 하나의 값이 아니라 구간(값 ± 반올림 오차)으로 보고, 식의 왼쪽 구간과 오른쪽 구간이 겹치는지를 본다. 덧셈과 곱셈, 나눗셈의 구간은 구간 산술의 규칙으로 계산한다. 정수는 반올림되지 않았다고 보고 오차를 0으로 둔다. 그래서 21 + 5 = 26은 구간이 점 하나이고, 23과 겹치지 않는다. 다만 왼쪽에 나눗셈이나 소수가 있고 결과가 정수로 적혀 있으면(16/18 = 89%) 정수로 반올림한 것으로 보고 ±0.5를 허용한다.

이 점검은 한계가 있다. 입력이 이미 반올림된 정수일 때(예: 1916년과 1111년으로 쓰인 두 값의 나눗셈) 정수의 반올림 오차를 0으로 두면 아주 작은 차이를 틀림으로 지적한다. 그래서 점검기는 상대 차이가 0.5% 미만이면 틀림(FAIL)이 아니라 경고(WARN, 코드 A3)로 낮춘다. 또 왼쪽과 오른쪽이 10, 100, 1000배만 다르면 코드 A2의 경고로 따로 낸다. 단위 환산(0.4 ka를 400년으로)일 수도 있고 소수점 오류일 수도 있어 기계가 가르지 못하기 때문이다.

**백분율과 표본 수(GRIM 방식).** 표본이 n명일 때 관측한 백분율은 k/n × 100(k는 0부터 n까지의 정수) 가운데 하나여야 한다. 논문이 "58.8%(n = 176)"라고 썼다면 소수 첫째 자리로 반올림하여 58.8이 되는 k가 있어야 한다. 176명에서 103명은 58.52%이고 104명은 59.09%여서 58.75~58.85에 드는 k가 없다. 이런 값은 n이 틀렸거나, 백분율의 분모가 n과 다르거나, 백분율이 틀린 것이다. 이 점검은 평균에 대해 제안된 방법(Brown & Heathers, 2017; 서지 확인 필요, 이 책은 읽지 못했다)을 비율에 옮긴 것이다. 평균보다 단순하며(k/n뿐이다), 이 책이 읽은 원 논문의 서술에 의존하지 않는다. 점검기는 "백분율 뒤 몇 글자 안에 n = 정수가 오는" 서식에만 적용하며, 그 서식이 아닌 곳의 백분율은 보지 못한다.

**표의 합.** 행의 한 열이 오른쪽 열들의 합이면(시료 수 = 형별 사람 수의 합) 그것이 합계 열이다. 점검기는 어느 열이 합계 열인지를 "행의 3분의 2 이상에서 맞는 열 가운데 가장 많이 맞는 열 하나"로 정한다. 이 조건을 느슨하게 하면(처음에는 2분의 1 이상이었다) 작은 수가 많은 표에서 우연히 맞는 열이 합계 열로 오인되어 정상 행을 지적한다(13.6절). 합계 줄은 첫 칸이 "합계"나 "합"인 마지막 줄이며 위쪽 줄의 열 합과 견준다.

</div>

이론 상자에서 나눈 대로, 이 장의 점검 절차는 모델을 부르기 전과 후, 사람이 보는 단계까지 일곱 걸음으로 이루어진다. 그림 13-1은 그 일곱 걸음과, 이 컨테이너에서 어느 걸음을 실행했고 어느 걸음을 실행하지 못했는지를 함께 보인다.

![환각 점검 절차의 일곱 걸음. 이 컨테이너에서 실행해 로그를 남긴 걸음은 1, 4, 5, 6이다. 2는 z840 실행 필요이고 3은 모델 출력 대신 이 책이 만든 시연값을 썼다. 7은 사람이 한다.](fig-ch13-flow-v1)

일곱 걸음의 이유를 하나씩 적는다.

**1. 원문을 고정한다.** 점검은 한 파일에 대해서만 한다. 원문이 바뀌면 점검 결과의 뜻이 사라진다. 파일의 SHA-256 해시(내용이 한 글자만 달라도 달라지는 짧은 지문)를 로그에 적는다. 이 장은 입력 네 개의 해시를 `make-inputs.log`에 적었다.

**2. 모델을 부른다.** 온도(다음 글자를 고를 때의 무작위성)를 0으로 하고 시드(난수의 출발값)를 고정한다. 그래도 같은 출력이 나온다는 보증은 없다(13.8절). 한 줄에 주장 하나만 쓰게 하고, 원문 문장을 옮길 때는 따옴표 안에 한 글자도 바꾸지 않게 하고, 원문에 없는 계산값은 줄 끝에 `[계산]`을 붙이게 한다. 이 서식 요구는 점검기가 인용과 숫자를 찾기 쉽게 하려는 것이다. 모델이 서식을 지킨다는 보증도 없으며 실제 모델에서는 확인하지 못했다.

**3. 모델 출력을 받는다.** 이 장은 이 걸음을 시연값으로 대신했다.

**4. 글자 점검.** 따옴표 안의 문장이 원문에 글자 그대로 있는가(Q), 숫자가 원문에 있는가(N), 숫자 뒤의 단위가 원문과 같은가(U).

**5. 계산 점검.** 식이 맞는가(A), 백분율이 표본 수에서 가능한가(G), 표의 행 합과 열 합이 맞는가(T), 확률과 연대와 좌표가 범위 안인가(R).

**6. 두 번 돌려 견준다.** 같은 입력으로 모델을 두 번 돌려 숫자가 달라지는 줄을 찾는다. 달라지는 곳은 모델이 흔들린 곳이다. 두 번 다 같은 틀린 값을 낼 수도 있으므로 같다고 맞다는 뜻은 아니다.

**7. 사람이 원문 쪽을 본다.** 지적된 줄과 함께, 통과한 줄 가운데 일부를 무작위로 골라 원문과 맞춰 본다. 통과한 줄에도 뜻의 오류가 있을 수 있기 때문이다.

## 13.5 환각 점검기의 구조와 단위 시험

점검기(`halluccheck-v1.py`, 668줄)는 표준 라이브러리만 쓴다. 세 가지 방식으로 실행한다.

```
$ python halluccheck-v1.py verify 모델출력.md 원문.md     # 모델 출력을 원문과 견준다
$ python halluccheck-v1.py self 문서.md                   # 한 문서 안의 모순을 찾는다
$ python halluccheck-v1.py diffruns 출력1.md 출력2.md      # 두 번의 실행을 견준다
```

`verify`는 모델 출력 문서의 줄마다 아래 일곱 가지 점검을 하고, `self`는 원문 없이 A, G, T, R만 한다. 모델이 없는 문서(제1권의 원고)에도 `self`를 돌릴 수 있다.

{{T:점검기의 점검 일곱 가지. 지적 부호의 첫 글자가 점검 이름이다. FAIL은 사람이 원문을 봐야 하는 지적이고 WARN은 참고이다}}

| 부호 | 점검 | 하는 일 | 모르는 것 |
|---|---|---|---|
| Q1 Q2 Q3 | 인용 | 따옴표(" ", “ ”, 「 」) 안 5자 이상의 글이 원문에 글자 그대로 있는지 본다. 공백만 정리해 같으면 통과, 공백과 부호를 모두 지우고 같으면 Q3(경고), 아니면 가장 비슷한 원문 문장을 찾아 유사도 0.70 이상이면 Q2, 미만이면 Q1 | 따옴표 없는 서술, 인용의 출처 |
| N1 | 숫자 | 모델 출력의 숫자가 원문에 같은 값으로 있는지 본다. 없으면 원문의 숫자 가운데 자리가 바뀐 것, 10의 거듭제곱 배, 부호가 뒤집힌 것, 한 자리만 다른 것을 후보로 붙인다. 줄에 `[계산]`이 있으면 파생값으로 보고 건너뛴다 | 값이 원문의 다른 곳에 있을 때의 오류 |
| U1 | 단위 | 같은 값이 원문에 있으나 붙은 단위가 다르면(bp와 kb) 지적한다 | 값이 같지 않을 때의 단위 |
| A1 A2 A3 | 산술 | `a + b = c`, `4/6 = 66.7%` 같은 식을 구간 산술로 견준다. 10배만 다르면 A2, 상대 차이가 0.5% 미만이면 A3(둘 다 경고) | 식이 아닌 서술, ±, √, 지수, 함수형 식 |
| G1 | 백분율 | `P%(n = N)` 서식에서 N명으로 만들 수 있는 백분율인지 본다 | 다른 서식, 분모가 다른 백분율 |
| T1 T2 | 표 | 마크다운 표에서 합계 열의 행 합(T1)과 합계 줄의 열 합(T2)을 본다 | 합계가 없는 표 |
| R1 R2 R3 | 범위 | 백분율 0~100, p 값 0~1, 상관계수 −1~1, BP 구간의 앞 수가 더 큼, 같은 방식의 연도 구간, 좌표 | 이 밖의 범위 |

각 점검은 작은 함수 하나이다. 가장 짧은 GRIM 방식의 점검(`check_grim`)은 다음과 같다.

```
GRIM_RE = re.compile(r'(?<![\d.])(\d+(?:\.\d+)?)\s*%[ ,(는은이가의]{0,5}n\s*=\s*(\d+)')

def check_grim(lines, stats):
    out = []
    for i, raw in enumerate(lines, 1):
        for m in GRIM_RE.finditer(raw):
            p, n = m.group(1), int(m.group(2))
            d = len(p.split('.')[1]) if '.' in p else 0       # 적힌 소수 자릿수
            pv = float(p)
            if n <= 0:
                continue
            tol = 0.5 * 10 ** (-d) + 1e-9                    # 반올림 구간의 반쪽
            ks = [k for k in range(0, n + 1) if abs(k * 100.0 / n - pv) <= tol]
            if not ks:                                       # 만들 수 있는 k 가 하나도 없다
                ... 가까운 세 값을 적어 F('G1', ...) 로 지적한다
    return out
```

백분율과 n 사이에 허용하는 글자를 `[ ,(는은이가의]{0,5}`로 좁힌 데에는 이유가 있다. 처음에는 "숫자가 아닌 글자 6개 이내"로 느슨하게 썼다가 제1권의 "임계 상관(양쪽 5%, 1%): n = 57이면"을 백분율 1%와 n = 57로 읽어 잘못 지적했다. 이 서식을 좁혀 이 오탐을 없앴다(13.9절).

#### 실습 13-6. 점검기의 단위 시험

**입력.** 이 책이 점검기의 동작을 보이려고 만든 짧은 글 40개(시연값). 맞는 글은 지적이 없어야 하고, 틀린 글은 기대한 부호의 지적이 있어야 한다. 예를 들면 `23명 = 21 + 5`는 A1, `4/6 = 66.7%`는 지적 없음, `O-M175(58.8%, n = 176)`은 G1, `p = 1.2`는 R1, `3600~4200 BP`는 R2이다.

**확인.** 단위 시험의 통과는 점검기가 이 40개의 경우에 대해 기대대로 동작한다는 뜻일 뿐이다. 점검기가 실제 글에서 잘 동작한다는 증명이 아니다.

**점검기가 못 본 네 가지.** X01~X04가 이 점검기의 구조적 한계를 보인다.

- X01(항목을 바꿔 붙임)은 12라는 숫자가 원문에 있으므로 숫자 점검을 통과하고, 12명이 "O3a"에 속한다는 서술은 산술식도 표도 범위도 아니어서 어느 점검에도 걸리지 않는다. 같은 숫자를 다른 항목에 붙이는 오류는 원문의 "문맥"을 이해해야 알 수 있다.
- X02(이름 바꿈)는 숫자가 없는 문장이다.
- X03(21을 12로)은 두 자리가 바뀐 전형적인 오류이지만, 12가 원문의 다른 곳에 있어서 "원문에 있는 숫자"로 통과했다. 원문이 넓을수록 이 일은 더 자주 일어난다(13.7절).
- X04(따옴표 없는 부정 서술)는 인용이 아니고 숫자도 없다. 모델이 인용 서식을 지키지 않고 의역으로 쓰면 인용 점검이 하나도 작동하지 않는다.

그림 13-1의 7단계(사람이 원문 쪽을 봄)가 필요한 이유가 이것이다.

**점검기의 지적이 모델의 오류가 아닌 경우.** S01과 S02는 모델이 원문을 충실히 옮겼는데도 지적된 줄이다. S01(23 = 21 + 5)은 제1권 11장 계산 11-1이 이미 "26이어서 맞지 않다"고 적은 원문의 어긋남이다. S02(58.8%, n = 176)는 13.9절에서 다룬다. 점검기가 지적한 줄을 보고 "모델이 틀렸다"고 결론 내리면 원문이 틀린 경우를 놓친다. 반대로 지적이 없다고 "원문과 같다"고 결론 내릴 수도 없다. 지적은 "사람이 원문 쪽을 볼 곳"이라는 뜻으로만 읽는다.

**찾은 두 가지와 이유.** 11-3은 제1권이 계산 11-1의 판정문, 11.10절의 목록, 장부 11-3의 세 곳에 식 `23 = 21 + 5`를 글자 그대로 적었기 때문에 점검기가 세 곳 모두에서 A1으로 지적했다(왼쪽 약 23, 오른쪽 약 26). 그러나 제1권이 논문의 문장을 처음 인용한 곳("23명이 SNP 증폭에 실패했거나(21) 일관된 결과를 내지 못했다(5)")은 식이 아니고 괄호 속 숫자이므로 점검기는 이 문장에서 어긋남을 찾지 못한다. 점검기는 **제1권이 어긋남을 식으로 풀어 적은 곳**을 찾았을 뿐, 논문의 서술에서 어긋남을 알아본 것이 아니다. 11-32도 같다. 장부의 줄과 본문의 판정문(866줄)이 "56.6%는 n = 127에서"의 서식으로 적혀 있어 G1 점검에 걸렸다. 같은 값이 적힌 다른 줄(본문 862줄, 에벤키 56.6%: 72/127 = 56.69%)은 서식이 달라 걸리지 않았다. 11-32의 계산 자체는 일치한다. 점검기가 밝힌 가까운 값 71/127 = 55.91%와 72/127 = 56.69%는 제1권이 계산 11-12c에서 쓴 값과 같다.

**못 찾은 아홉 가지와 이유.**

- 11-5는 13.7%와 1/6을 잇는 식이나 n이 적혀 있지 않다. 표의 칸이 어느 유적의 것인지를 이해하고 그 유적의 시료 수(6)로 백분율을 견주는 점검(표 안의 GRIM)이 있어야 하는데 점검기에는 없다.
- 11-7, 11-8, 11-25는 뜻의 문제이다. 어느 짝인지, 글과 표가 맞는지는 글자와 산술로 정해지지 않는다.
- 11-36은 EPS(연대표가 이상적인 연대표와 얼마나 같은가를 나타내는 지표)를 계산하는 식을 점검기가 모른다. 11-39는 곱셈이 맞고, 그 결과를 논문의 다른 값 0.53과 견주는 일은 두 숫자를 같은 양으로 이어 주는 서술이 필요하다. 11-41은 p 값과 유의 수준의 해석, 11-43은 두 수의 크기 비교 서술, 11-46은 "30건"의 정체가 본문에 없다는 점으로 모두 점검기의 범위 밖이다.

**제1권이 지적하지 않았으나 점검기가 새로 지적한 것.**

- 11.3.6절(359줄)과 장부 11-18의 "O-M175(58.8%, n = 176)"와 "몽골인 C3가 50.7%(n = 285)"가 G1으로 지적되었다. 176명에서 만들 수 있는 가까운 값은 102/176 = 57.95%, 103/176 = 58.52%, 104/176 = 59.09%이고, 285명에서는 143/285 = 50.18%, 144/285 = 50.53%, 145/285 = 50.88%이다. 소수 첫째 자리로 반올림해 58.8이나 50.7이 되는 값이 없다. 같은 문장의 다른 세 값(80%, n = 5; 53%, n = 304; 94%, n = 184)은 가능한 값이었다. 에벤키 C3c1 56.6%(n = 127)는 제1권이 이미 같은 이유로 지적했다.
- 이 세 값을 그림 13-4에 그렸다. 세로선이 가능한 k/n이고 파란 띠가 적힌 값의 반올림 구간이다. 띠 안에 가능한 값이 없다.

![백분율과 표본 수로 만들 수 있는 값. 세로선은 k/n × 100이고 파란 띠는 적힌 값(소수 첫째 자리)의 반올림 구간 ±0.05이다. 세 경우 모두 띠 안에 가능한 값이 없다.](fig-ch13-grim-v1)

이것이 논문의 오류라는 증거는 아니다. 가능한 설명은 (가) 백분율의 분모가 n과 다르다(예: 표 2가 여러 연구의 값을 합친 것이어서 n이 다른 집단의 시료 수), (나) n이 틀렸다, (다) 백분율이 틀렸다, (라) 제1권이 논문에서 옮길 때 틀렸다이다. 이 책은 논문을 읽지 못했고 제1권의 옮겨 적은 글을 입력으로 썼으므로 (라)도 배제하지 못한다. **원문 쪽 확인 필요.** 제1권의 장부 11-18("직접(주장)")의 수준은 이 장에서 바꾸지 않았다. 새 후보로 추가하는 것은 제1권을 고칠 때의 일이다.

**점검기가 낸 나머지 지적(오탐이 아닌 경고).** 본문의 A2 둘(7.90 − 7.50 = 400년, 8.0 − 7.475 = 525년)은 ka를 년으로 바꾼 정상적인 단위 환산이다(0.4 ka = 400년). A3 하나(1916 ÷ 1111 = 1.724, 상대 차이 0.033%)는 반올림된 입력의 전파이다. 1 ÷ (0.0025 × 9) × 25 = 1111.11년으로 계산하면 1916 ÷ 1111.11 = 1.7244이고 소수 셋째 자리로 1.724이다(`check-1916.log`). 제1권의 값이 맞다.

**제1권과의 일치.** 본문에서 검사한 산술식 119개 가운데 114개는 통과했고, 5개가 지적되었다(제1권이 이미 적은 23 = 21 + 5의 두 곳, 단위 환산 둘, 반올림 하나). 제1권 원고의 값 가운데 이 점검에서 제1권이 이미 적은 것 말고 어긋난 값은 없었다. 이 말은 119개 식에만 해당한다. 점검기가 건너뛴 44개 식과 점검 대상이 아닌 서술에 대해서는 아무것도 말하지 않는다.

**점검기를 고친 이력.** 이 결과도 점검기를 한 번 고친 뒤의 것이다. 제1권 본문에 처음 돌렸을 때(`eval-vol1-run1.log`, 점검기 판은 `halluccheck-v1.run2.py.txt`)는 본문 19건과 장부 3건, 모두 22건이 지적되었다. 이 가운데 12건이 점검기의 오탐이었고, 3건은 틀림(FAIL)이 아니라 경고(WARN)여야 했다.

## 13.10 모델 호출부: Ollama 서버에 요청하고 결과를 점검기로 넘긴다

**이 절의 코드는 이 컨테이너에서 모델과 통신해 보지 못했다. z840 실행 필요.** 이 컨테이너에서 확인한 것은 세 가지이다. 문법 검사, 요청 본문을 만들어 보이는 `--dry-run`(서버에 접속하지 않음), 서버가 없을 때의 실패 경로.

코드(`llm-client-v1.py`, 108줄)의 핵심은 다음과 같다.

```
SYSTEM = (
    '너는 논문 원문에서 주장과 숫자를 옮겨 적는 도구이다. 원문에 없는 내용을 더하지 않는다. '
    '규칙: (1) 한 줄에 주장 하나만 쓴다. (2) 원문 문장을 그대로 옮길 때는 큰따옴표 안에 한 글자도 바꾸지 말고 쓴다. '
    '(3) 숫자는 원문에 적힌 그대로 쓰고 단위를 붙인다. (4) 원문에 없는 값을 계산해 쓸 때는 줄 끝에 [계산] 을 붙이고 식을 함께 쓴다. '
    '(5) 표는 마크다운 표로 쓰고 합계 줄은 첫 칸을 합계로 쓴다. (6) 원문에 없으면 "원문에 없음"이라고 쓴다.'
)

def build_payload(model, source_text, task, temperature, seed, num_ctx):
    user = '다음 원문에서 %s\n\n--- 원문 시작 ---\n%s\n--- 원문 끝 ---' % (task, source_text)
    return {
        'model': model,
        'stream': False,
        'messages': [{'role': 'system', 'content': SYSTEM}, {'role': 'user', 'content': user}],
        'options': {'temperature': temperature, 'seed': seed, 'num_ctx': num_ctx},
    }

def call_ollama(host, payload, timeout):
    req = urllib.request.Request(host.rstrip('/') + '/api/chat', data=json.dumps(payload).encode('utf-8'),
                                 headers={'Content-Type': 'application/json'}, method='POST')
    with urllib.request.urlopen(req, timeout=timeout) as r:
        return json.loads(r.read().decode('utf-8'))
```

`main`은 이 요청을 `--runs` 횟수만큼 보내 응답의 `message.content`를 `output-1.md`, `output-2.md`로 저장하고, 곧바로 `halluccheck`의 `verify`를 같은 원문에 돌려 지적을 출력한다. 요청 본문의 해시와 원문의 해시, 모델 이름, 온도, 시드를 `meta-N.json`에 남긴다.

이 코드가 확인하지 못한 가정은 다음과 같다.

1. 엔드포인트 `/api/chat`, 포트 11434, 요청 필드 `model`, `messages`, `stream`은 제3자의 글(Geshan, 2025)에서 읽었다. 공식 문서는 읽지 못했다.
2. `options` 안의 필드 이름(`temperature`, `seed`, `num_ctx`)과 응답에서 글이 있는 위치(`message.content`)는 이 책이 어디서도 확인하지 못했다. 응답에서 `message.content`를 찾지 못하면 코드는 종료 코드 3으로 끝나고 응답의 키를 보인다(이 경로도 실행하지 못했다).
3. 문맥 길이 `num_ctx = 8192`는 이 책이 정한 값이다. 11.3절(한글 4,592자를 포함한 11,928자)이 모델의 토큰으로 몇 개인지 이 책은 모른다. 원문이 문맥 길이를 넘으면 앞부분이 잘릴 수 있다고 알려져 있으나 이 책은 확인하지 못했다.
4. 지시문은 이 책이 재현을 위해 코드에 직접 적었다. 지시문을 여러 곳에서 쓰거나 자주 바꾼다면 코드 밖에 두고 이름으로 불러 쓰는 편이 낫다.

## 13.11 한계와 함정

**모델을 실행하지 못했다.** 이 장의 가장 큰 한계이다. 모델이 표를 얼마나 정확히 옮기는지, 한국어와 영어 논문에서 어떻게 다른지, 어떤 크기의 모델이 이 일에 쓸 만한지는 이 장이 아무것도 말하지 않는다.

**시연 출력은 모델이 쓴 것이 아니다.** 심은 오류의 종류와 개수는 이 책이 정했다. "찾도록 설계한 오류 10개 중 10개"는 점검기의 성능이 아니라 설계가 의도대로 동작한다는 확인이다.

**원문은 논문이 아니다.** 이 장의 원문 대역은 제1권 11장 원고이다. 제1권이 논문을 틀리게 옮겼다면 점검기는 그 틀림을 모른다. 실제로 쓸 때는 논문 PDF에서 뽑은 글을 원문으로 쓰되, 뽑는 단계(2장)에서 이미 열이 흩어질 수 있음을 기억한다.

**점검기가 통과한 줄이 맞다는 뜻이 아니다.** X01~X04에서 보았듯 같은 숫자를 다른 항목에 붙이거나 이름을 바꾸거나 부정문을 뒤집은 오류는 점검기를 통과한다. 통과한 줄의 일부를 사람이 원문과 맞춰 본다.

**점검기가 지적한 줄이 모델의 오류라는 뜻도 아니다.** 원문의 어긋남을 충실히 옮겨도 지적된다(S01, S02). 지적은 사람이 원문 쪽을 볼 곳이다.

**서식에 의존한다.** 인용 점검은 따옴표가 있어야, 파생값 표시는 `[계산]`이 있어야, GRIM 점검은 `P%(n = N)` 서식이 있어야, 표 점검은 마크다운 표가 있어야 작동한다. 모델이 서식을 지키지 않으면 점검이 조용히 사라진다. 점검기가 얼마나 많은 항목을 검사했는지를 요약에 함께 적는 이유이다. 본문 119개 식 가운데 44개를 건너뛴 것처럼, 검사하지 못한 항목의 수도 결과의 일부이다.

**기준값은 조정한 값이다.** 합계 열의 3분의 2, 상대 차이 0.5%, 인용 유사도 0.70은 이 책이 정했다. 근거가 되는 연구가 없다. 다른 값을 쓰면 지적이 달라진다. D10은 유사도 0.67이어서 "근사"(Q2)가 아니라 "없음"(Q1)으로 분류되었는데, 기준이 0.65였다면 Q2였을 것이다.

**원문 범위.** 원문이 넓을수록 "숫자가 원문에 있다"는 통과가 헐거워진다(13.7절). 점검하는 주장의 출처 쪽으로 원문을 좁힌다.

**한 번의 점검은 한 번의 점검이다.** 같은 문서에 점검기를 고쳐 가며 돌린 이력(13.6절, 13.9절)이 보이듯 점검기도 틀린다. 점검기의 오탐은 사람이 보고, 점검기의 단위 시험(13.5절)에 사례를 추가하는 식으로 되풀이해 고친다.

**모델의 응답을 점검기에 그대로 믿고 맡기지 않는다.** 모델이 낸 숫자를 그대로 책이나 서비스에 싣는 경로를 만들지 않는다. 점검기를 통과하고 사람이 본 값만 쓴다.

**라이선스.** 이 책이 확인한 라이선스는 프로그램(llama.cpp, llama-cpp-python)의 작성자 표기뿐이다. 모델 가중치의 이용 조건은 모델마다 다르며 읽지 못했다(13.3절). 모델 출력을 출판물에 쓸 때의 조건도 모델 카드를 읽어야 한다.

**개인정보와 저작권.** 로컬에서 돌리는 것의 이점은 원문이 밖으로 나가지 않는다는 점이다. 그러나 이 책은 이를 확인하지 못했다. 서버가 외부로 통신하는지는 이 책이 점검하지 않았다.
