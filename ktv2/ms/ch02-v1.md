# 2장 논문과 자료를 모으는 법: 논문 검색 API, 전문과 PDF, 표 추출, 메타데이터 DB

제1권은 논문의 숫자를 손으로 다시 계산하며 읽었다. 그때 자주 걸린 곳이 있다. 논문의 표를 컴퓨터가 읽을 수 있는 글자로 바꾸면 열이 흩어져 나오는 일이다. 제1권 원고에서 "원문 쪽 확인 필요"라고 적은 줄은 8장, 9장, 10장, 11장, 13장에 모두 25줄이고(실습 2-9), 그 가운데 상당수가 표의 열이 흩어져 읽혀 짝을 이 책이 맞추었다는 서술이다. 이 장은 그 앞 단계, 곧 논문을 찾고, 내려받고, 표를 꺼내고, 그것들을 데이터베이스에 정리하는 일을 다룬다. 순서는 네 단계이다. 논문 검색 API를 정중하게 쓰는 법(2.2, 2.3절), 메타데이터를 담는 SQLite 데이터베이스의 설계(2.4절)와 시연 자료로 끝까지 돌려 보기(2.5절), PDF에서 표를 꺼내는 방법과 그 한계(2.6, 2.7절), 열이 흩어진 표를 산술로 걸러내고 되짜맞추는 방법(2.8절)이다.

이 장의 기술은 정직하게 두 갈래로 나뉜다. 한쪽은 이 컨테이너에서 실제로 실행한 것이다. PDF에서 표를 꺼내는 실험(실습 2-6~2-8), 제1권 데이터베이스를 읽는 일(실습 2-4), 데이터베이스 스키마와 적재 코드(실습 2-5)가 그렇다. 다른 한쪽은 실행하지 못한 것이다. 이 컨테이너의 셸은 논문 사이트와 API에 접속할 수 없어서(실습 2-0) 검색 API를 실제로 호출하지 못했다. 그래서 호출 스크립트(`apiclient.py`)는 만들되 "실행 확인 필요(z840에서 실행)"로 표시하고, 같은 스크립트를 이 컨테이너 안에서 돌아가는 가짜 서버에 겨누어 요청 속도 조절과 오류 처리, 해석, 적재 코드를 실제로 실행했다. 가짜 서버가 돌려주는 응답은 이 책이 만든 시연값이다. 시연값으로 얻은 숫자는 어떤 논문이나 서비스의 증거도 아니고, 코드가 의도대로 움직이는지를 보이는 것뿐이다.

**이 장이 하지 않는 것.**

- OpenAlex, Crossref, Unpaywall 같은 서비스에 실제로 접속하지 않았다. 이 컨테이너의 접속은 프록시가 거부한다(403, 실습 2-0). 우회하지 않았다. API 호출 스크립트는 모두 "실행 확인 필요(z840에서 실행)"이다.
- 시연 응답(JSON)의 필드 이름은 이 책이 알던 구조를 흉내 낸 것이다. 필드 이름을 담은 공식 문서 페이지는 이 책의 WebFetch 허용 목록 밖이어서 읽지 못했다(2.2절). 실제 응답과 대조해야 하며, 그 대조 함수(`probe_fields`)를 코드에 넣었다.
- 서비스의 이용 조건은 WebFetch로 읽은 페이지에서 옮긴 것만 적었다. WebFetch는 페이지를 요약해서 돌려주므로 문구가 원문과 정확히 같다고 보장할 수 없다. 원문 대조는 "확인 필요"로 남긴다. 읽은 날은 모두 2026년 10월 26일이다.
- Unpaywall(오픈 액세스 판 찾기 서비스)의 공식 문서는 자바스크립트 없이는 내용이 나오지 않아 읽지 못했다. 그래서 Unpaywall 호출 코드는 싣지 않는다.
- 실제 논문 PDF를 내려받아 저장하는 일은 하지 않았다. 시연 PDF 두 개를 이 책이 만들어 썼다.
- 표 추출은 제1권 조판 PDF(674쪽)와 이 책이 다시 조판한 시연 PDF에서만 시험했다. 학술지 PDF의 병합 셀, 회전된 표, 쪽을 넘어가는 표, 스캔 이미지의 표(광학 문자 인식, OCR)는 시험하지 않았다.
- 새 데이터베이스를 z840의 `/data/safe/dball2/ktv_db`에 두는 원칙은 목차안에서 옮겼다. 이 컨테이너에서는 그 경로를 확인할 수 없다(z840 확인 필요).
- GPU는 쓰지 않는다. 가장 오래 걸린 실행(시연 PDF 108장 만들기)이 377초였고 모두 CPU이다.

**이 장에서 확인한 일곱 가지.**

1. 가짜 서버(직전 요청과 0.20초 안에 오면 429를 돌려주도록 이 책이 정함)에 같은 요청 10건을 보냈을 때, 요청 사이에 간격을 두지 않은 클라이언트는 서버가 받은 19번의 요청 가운데 429를 9번 받았고 끝내는 데 2.25초가 걸렸다. 0.30초 간격을 둔 클라이언트는 10번을 보내 429가 0번이었고 2.70초가 걸렸다. 서두른다고 빨라지지 않았다(실습 2-2). 403을 받으면 다시 시도하지 않고 1번에서 멈추었다.
2. 제1권 데이터베이스(papers 74줄, refs 109줄)에 DOI 정규화를 적용했다. papers의 DOI 칸 74줄 가운데 73줄은 이미 정규형이었고 1줄은 DOI가 아닌 `openalex:W3187374414`였다. refs 109줄 가운데 51줄은 DOI 칸이 비어 있었다. 서로 다른 DOI는 52개이고, papers와 겹치는 것이 46개, refs에만 있는 것이 6개, papers에만 있는 것이 28개였다. 새 상태 규칙으로 옮기면 80줄(pdf 65, cited 15)이 된다(실습 2-4).
3. 시연 자료로 검색 응답 받기에서 DB 적재까지 돌렸다. 참고문헌 6줄이 4줄로 합쳐졌고(DOI 없는 1줄 제외, 같은 DOI 1줄 합침), 검색으로 찾은 둘을 더해 6줄이 되었으며 상태는 cited 2, abstract 2, pdf 2가 되었다. 출처끼리 연도가 다른 1건은 덮어쓰지 않고 기록했고, 랜딩 페이지(HTML)를 PDF로 받는 일은 첫 바이트 검사로 걸러졌다(실습 2-5).
4. 제1권 조판 PDF의 표 36개(정답 행 394줄)에서 pdfplumber의 선 기준 추출은 394줄 모두를 칸 배열까지 정확히 되살렸다. 같은 라이브러리의 글자 위치 기준은 1줄(0.3%), `pdftotext -layout`은 324줄(82.2%)이었다(실습 2-6). 이 PDF는 이 책이 직접 만들어 표에 선이 있으므로, 이 결과는 쉬운 경우의 값이다.
5. 같은 36개 표를 선 없이, 글자를 열 순서로 써서 다시 조판한 시연 PDF에서는 선 기준이 0줄, `pdftotext -raw`와 pdfplumber의 글자 흐름 읽기가 0줄을 되살렸고, 글자 좌표를 쓰는 방법(`-layout` 370줄, 글자 위치 기준 274줄)은 조판 순서와 무관하게 같은 값을 냈다(실습 2-7).
6. 학술지 PDF에서 뽑은 글자열(제1권 데이터베이스에 있는 한 논문의 표 2 부분)은 숫자 169줄이 열 단위로 흩어져 있었다. 읽힌 순서대로 세 개씩 접으면 22행 가운데 4행에서만 "AC + NC = 합계"가 성립했다. 행의 합과 비율을 제약으로 걸고 짝을 찾자 17개 행이 모두 하나씩 정해졌고(거짓 짝 후보 0), 제1권이 옮겨 적은 표와 17행 모두 같았다. 다만 행 합 점검만으로는 두 열의 방향이 정해지지 않았다(2의 17제곱 가지). 방향은 이웃 연도의 변화 강도로 2가지까지, 본문의 기준값 두 개로 1가지까지 줄었다(실습 2-8).
7. 그 표의 1986년 행은 AC + NC - 합계가 -0.02이다. 세 값이 모두 소수 둘째 자리로 반올림되었다면 0.015를 넘을 수 없으므로 이 행은 반올림으로 설명되지 않는다. 글자열에도 같은 세 값이 있어 제1권이 옮기다 틀린 것은 아니다. 원문 쪽 확인 필요(실습 2-8).

## 2.2 논문 검색 API와 이용 조건

#### 이론 배경: 검색 API는 무엇을 돌려주고, 왜 이용 조건을 먼저 읽는가

논문을 찾는 가장 쉬운 길은 검색 사이트에 단어를 넣는 것이다. 수십 편이면 그것으로 충분하다. 수백, 수천 편을 모으려면 사람이 화면을 누르는 대신 프로그램이 서버에 주소를 보내 답을 받아야 한다. 이때 쓰는 약속이 API이다. 논문 서지 정보(제목, 저자, 연도, 학술지, 초록, DOI, 인용 관계, 오픈 액세스 여부)를 돌려주는 대표적인 공개 서비스로 OpenAlex와 Crossref가 있다. 둘은 성격이 다르다. Crossref는 출판사가 DOI를 등록할 때 내는 서지 정보가 중심이어서 DOI를 가진 자료를 DOI로 묻기에 알맞다. OpenAlex는 여러 출처를 묶어 만든 대형 목록이어서 저자, 기관, 주제, 인용 관계와 오픈 액세스 위치까지 한 번에 묻기 좋다. (이 설명은 이 책이 읽은 페이지에서 확인한 것이 아니라 일반적인 소개이며, 각 서비스의 자료 범위는 확인 필요이다.)

API는 무료여도 공짜로 아무렇게나 쓰는 것이 아니다. 서버가 처리하는 요청의 수에는 한도가 있고, 한도를 넘으면 429라는 답이 오며, 심하면 차단된다. 한도의 숫자와 기준(초당 몇 번, 하루 몇 번, 동시에 몇 개)은 서비스가 정하고 바꾸기도 한다. 그래서 코드를 쓰기 전에 공식 문서의 현재 값을 읽어야 하고, 읽은 날짜를 적어 두어야 한다. 이 책이 읽은 두 서비스에서도 문서와 한도가 바뀐 흔적이 보였다(아래 표).

**쉬운 예(시연값).** 한 편의 DOI를 서버에 묻는 요청은 "이 번호의 논문 정보를 주세요"라는 주소 한 줄이다. 서버는 JSON으로 제목, 저자, 연도 등을 돌려준다. 같은 요청을 1초에 100번 보내면 서버 한 대를 혼자 쓰는 셈이 된다. 서버는 이를 막으려고 429를 돌려주고, 연락처가 없는 요청이 계속되면 차단한다.

## 2.3 정중하게 요청하기: 간격, 연락처, 429와 403

<div class="theory" markdown="1">

#### 이론 배경: 서버는 왜 거절하고, 클라이언트는 어떻게 물러서는가

서버 입장에서 요청 한 건은 CPU 시간과 데이터베이스 조회 한 번이다. 한 사람이 1초에 수십 건을 보내면 다른 사람들의 몫이 줄어든다. 그래서 서버는 한도를 넘는 요청에 429를 돌려주고, 그것도 무시하는 상대는 403으로 막는다. 클라이언트(요청을 보내는 쪽)가 지킬 규칙은 단순하다.

1. 요청 사이에 최소 간격을 둔다. 한 번에 한 요청만 보낸다(동시 요청 없음).
2. 연락처를 알린다. 문제가 생기면 서버 운영자가 먼저 연락할 수 있다.
3. 429를 받으면 기다렸다가 다시 한다. 기다리는 시간은 늘려 간다(백오프). 서버가 `Retry-After` 머리말로 기다릴 시간을 알려 주면 그에 따른다(일반적인 HTTP 규약이며 이 책이 읽은 두 API 문서에서는 확인하지 못했다).
4. 403은 다시 시도하지 않는다. 차단일 수 있으므로 멈추고 이유를 점검한다.
5. 한 번 받은 것은 저장해 두고 다시 받지 않는다(이 장의 `sources` 표가 응답 원문을 보존하는 까닭이다).

**쉬운 예(시연값).** 서버가 "직전 요청과 0.20초 안에 오면 429"라는 규칙을 가졌다고 하자. 0.30초마다 하나씩 보내면 모두 통과한다. 간격 없이 연달아 보내면 첫 요청만 통과하고 그 뒤는 429이다. 429를 받은 클라이언트가 곧바로 다시 보내면 또 429이다. 기다렸다가 다시 보내야 통과한다.

</div>

이 장의 클라이언트(`apiclient.py`)의 핵심은 두 부분이다. 하나는 서버(호스트)마다 직전 요청과의 간격을 재는 `Throttle`이고, 다른 하나는 상태 코드에 따라 갈리는 `Client.get`이다. 아래는 `Client.get`의 본체이며, 이 코드는 실제 서버에 대해서는 실행 확인 필요(z840에서 실행)이다.

```python
def get(self, path, params=None, raw=False):
    url = path if path.startswith('http') else self.base + path
    th = self.ths.setdefault(urlparse(url).netloc, Throttle(self.min_interval))
    q = dict(self.params) if url.startswith(self.base) else {}   # api_key와 mailto는 다른 서버(출판사)로 새지 않게 한다
    q.update(params or {})
    for attempt in range(self.max_retries + 1):
        th.wait()
        r = self.s.get(url, params=q, timeout=self.timeout)
        if r.status_code == 200:
            return r if raw else r.json()
        if r.status_code == 403:
            raise RuntimeError('403: 차단일 수 있다. 다시 시도하지 말고 ...')
        if r.status_code == 404:
            return None
        if r.status_code == 429 or r.status_code >= 500:
            ra = r.headers.get('Retry-After')
            wait = float(ra) if ra and ra.replace('.', '', 1).isdigit() else self.backoff0 * 2 ** attempt
            time.sleep(wait * (0.8 + 0.4 * random.random()))     # 흔들림을 섞어 여럿이 동시에 되돌아오지 않게
            continue
        r.raise_for_status()
    raise RuntimeError('재시도 한도 초과: ' + url)
```

## 2.4 메타데이터 DB의 설계: 제1권의 철학을 잇고 DOI로 하나로 묶기

<div class="theory" markdown="1">

#### 이론 배경: 논문 목록을 표 하나로 만들면 왜 곧 무너지는가

논문 목록을 엑셀 한 장으로 시작하는 일은 흔하다. 수십 편일 때는 문제가 없다. 수천 편이 되고 여러 출처(검색 API 둘, 참고문헌 목록, 직접 내려받은 PDF)에서 같은 논문이 여러 번 들어오면 세 가지 문제가 생긴다. 첫째, 같은 논문이 여러 줄이 된다. DOI를 `https://doi.org/10.1000/ABC`, `doi:10.1000/abc`, `10.1000/abc.`처럼 달리 적으면 사람 눈에는 같아도 프로그램은 다른 값으로 본다. 둘째, 출처끼리 값이 다르면(예: 한 곳은 2021년, 다른 곳은 2022년) 나중에 들어온 값이 앞의 값을 덮어쓰고, 덮어썼다는 사실도 남지 않는다. 셋째, 어디까지 모았는지를 알 수 없다. 서지만 아는 논문, 초록까지 받은 논문, PDF까지 가진 논문이 한 표에 섞여 있으면 "다음에 무엇을 받을까"를 정할 수 없다.

관계형 데이터베이스는 이 셋을 설계로 푼다. (1) 고유한 열(DOI)을 정하면 같은 DOI는 한 줄만 들어간다. (2) 원문 응답을 따로 두고 해석 결과만 논문 표에 두면, 해석을 고쳐도 원문에서 다시 만들 수 있다. (3) 충돌은 덮어쓰지 않고 따로 적는다. (4) 단계를 나타내는 열(status)을 두고 올라가기만 하게 하면 "다음에 받을 것"이 질의 하나로 나온다.

**쉬운 예(시연값).** 같은 논문이 OpenAlex에서 한 번, Crossref에서 한 번, 참고문헌 목록에서 두 번(서로 다른 DOI 표기) 들어왔다고 하자. 네 번 들어와도 DOI를 정규화하면 논문 표에는 한 줄이다. 원문 표에는 응답 두 개가 남고, 연도가 2022년과 2021년으로 다르면 충돌 표에 한 줄이 남는다.

</div>

**제1권 데이터베이스의 구조.** 제1권의 책 DB(`db/ktv1bookdb-v14.sqlite`)는 책 한 권의 장, 절, 주장, 계산, 도구, 데이터 표 등을 담는 열 몇 개의 표로 이루어져 있다. 이 장이 이어받는 것은 두 표이다. `papers`는 열이 `id, doi, title, authors, year, journal, status, chapters, sha256, fulltext`이고 74줄이다. `refs`는 열이 `id, chapter_id, apa, doi`이고 109줄이다. 철학은 두 가지로 읽힌다. 하나는 참고문헌 한 줄(`refs`, 서지 문장 전체와 DOI)과 논문 한 편(`papers`, 서지와 전문)을 구별한 것이고, 다른 하나는 파일의 지문(`sha256`)과 추출한 전문(`fulltext`)을 논문 줄에 같이 둔 것이다. 새 DB는 이 둘을 그대로 잇고, 위에 말한 네 가지 설계(원문 보존, 충돌 기록, 단계 상태, DOI 고유)를 더한다.

**DOI 정규화.** 정규화 함수 `doi_norm`은 다섯 가지를 한다. 주소 인코딩(`%2F`)을 풀고, 앞뒤 공백을 자르고, `https://doi.org/`, `http://dx.doi.org/`, `doi:` 접두어를 떼고, `10.`으로 시작하는 DOI 부분을 찾고, 문장 끝에 붙어 온 기호(마침표, 쉼표, 짝이 맞지 않는 닫는 괄호 등)를 벗기고 소문자로 바꾼다. 마지막 소문자 처리는 DOI가 대소문자를 구별하지 않는다는 전제에 기대는데, 이 책은 그 전제를 공식 문서로 확인하지 못했다(확인 필요). 제1권 DB가 DOI 74줄 가운데 73줄을 소문자로 저장한 관행을 따랐다.

![메타데이터 DB의 표와 관계. works가 중심이고 sources(응답 원문), refs(서지 한 줄), conflicts(출처끼리 다른 값), extracted_tables(추출한 표)가 work_id로 이어진다. fetch_log는 어느 표와도 이어지지 않는 요청 기록이다.](fig-ch02-schema-v1)

핵심인 `works`의 정의는 다음과 같다.

```sql
CREATE TABLE IF NOT EXISTS works(
  id        INTEGER PRIMARY KEY,
  doi       TEXT UNIQUE,            -- 정규화한 DOI(소문자, 접두어 없음). DOI가 없는 자료는 NULL
  ext_id    TEXT UNIQUE,            -- DOI가 없을 때의 다른 식별자(예: openalex:W...)
  title     TEXT, authors TEXT, year INT, journal TEXT, abstract TEXT,
  status    TEXT NOT NULL DEFAULT 'cited' CHECK(status IN ('cited','abstract','pdf')),
  oa_status TEXT, pdf_url TEXT, pdf_path TEXT, sha256 TEXT, fulltext TEXT,
  chapters  TEXT,                   -- 인용한 장(제1권 papers.chapters와 같은 뜻)
  first_seen TEXT, updated TEXT,
  CHECK(doi IS NOT NULL OR ext_id IS NOT NULL));
```

상태 열의 세 값은 "이 책이 그 논문에 대해 무엇을 가졌는가"를 나타낸다. `cited`는 서지(적어도 DOI나 인용문 한 줄)만 아는 단계이다. `abstract`는 제목과 초록을 받은 단계, `pdf`는 PDF 파일을 받아 지문(SHA-256)을 계산하고 글자를 추출해 둔 단계이다. 숫자가 올라가는 방향으로만 바꾼다(`RANK = cited 1, abstract 2, pdf 3`). 한 번 `pdf`가 된 논문이 나중에 참고문헌 목록에서 다시 들어와 `cited`로 내려가는 일은 없어야 하기 때문이다(실습 2-5에서 확인).

**저장 위치.** 목차안(제2권 목차안 6항)은 새 DB를 z840의 `/data/safe/dball2/ktv_db`에 두기로 했다. 이 컨테이너에서는 그 경로가 있는지, 쓰기 권한이 있는지, 여유 공간이 얼마인지 확인할 수 없다(z840 확인 필요). 이 장의 실습은 `ms/code/ch02/out/` 아래에 시연 DB(`demo-ktvdb.sqlite`)를 만들었으며 실제 DB와 섞이지 않는다. 실제 DB를 만들 때 지킬 규칙은 세 가지이다. DB 파일 하나(`ktvdb-v1.sqlite`)와 PDF 폴더를 같은 상위 폴더에 두고, PDF 경로는 DB 안에 상대 경로로 적고(폴더를 옮겨도 깨지지 않게), PDF 파일 이름은 DOI에서 만든 이름이 아니라 지문(SHA-256)의 앞 16자로 짓는다(DOI에는 `/`와 `(`가 들어 있어 파일 이름으로 위험하다). 마지막 규칙은 이 장에서 실행하지 않았다.

## 2.6 PDF에서 표를 꺼내기: 제1권 조판 PDF로 시험하기

<div class="theory" markdown="1">

#### 이론 배경: PDF는 표를 모른다

PDF는 "이 글자를 이 좌표에 그려라"와 "이 선을 이 좌표에 그어라"라는 명령의 묶음이다. 사람 눈에는 표로 보여도 파일 안에는 표라는 구조가 없다. 칸도, 행도, 열도 없고 글자 조각과 선분이 있을 뿐이다. 그러므로 표 추출은 구조를 복원하는 추측이다. 추측의 단서는 크게 둘이다.

첫째는 선이다. 칸막이 선이 그어진 표라면 선분이 만나는 곳을 찾아 칸을 나누고, 칸 안에 들어온 글자를 칸에 담으면 된다(선 기준, lattice). 둘째는 글자의 위치이다. 선이 없는 표라면 같은 줄에 놓인 글자를 한 행으로, 세로로 정렬된 글자를 한 열로 묶는다(글자 위치 기준, stream 또는 text). 이 방법은 열 사이의 빈 공간이 충분하다는 가정에 기댄다.

여기에 셋째 단서가 있지만 믿을 수 없다. 글자가 파일에 쓰인 순서(글자 흐름, content stream order)이다. 한 행씩 왼쪽에서 오른쪽으로 쓴 PDF라면 이 순서가 곧 표의 읽는 순서이다. 그러나 조판 프로그램에 따라서는 열 하나를 위에서 아래로 다 쓰고 다음 열로 넘어가기도 하고, 쓰는 순서가 화면 위치와 관계가 없기도 하다. 이 경우 글자 흐름을 따라 읽으면 열이 흩어져(scatter) 나온다. 이것이 이 장 첫머리에서 말한 "열이 흩어지는 문제"이다.

**쉬운 예(시연값).** 3행 2열 표 `(가, 1), (나, 2), (다, 3)`이 있다고 하자. 행 순서로 쓴 PDF의 글자 흐름은 `가 1 나 2 다 3`이고, 열 순서로 쓴 PDF는 `가 나 다 1 2 3`이다. 두 PDF는 화면에서 똑같은 표로 보인다. 글자 흐름을 두 개씩 끊어 읽는 프로그램은 앞의 PDF에서는 표를 되살리고 뒤의 PDF에서는 `(가, 나), (다, 1), (2, 3)`이라는 틀린 표를 내놓는다. 틀렸다는 사실을 프로그램은 모른다.

</div>

이 절의 시험 자료는 제1권 조판 PDF(`/home/claude/book/build/book-color-v20.pdf`, 674쪽)이다. 정답은 제1권 원고(마크다운)의 표이다. 원고의 표 캡션 178개를 모두 PDF에서 쪽까지 찾았고, 그중 열이 3개 이상, 행이 3개 이상, 숫자 칸의 비율이 0.5 이상인 표 36개를 골랐다(행 중앙값 8, 열 중앙값 6). 정답 행은 394줄, 정답 칸은 2,491개이다. 한 행이 "온전하다"는 것은 뽑은 칸의 배열과 글자(공백은 뺌)가 정답과 모두 같다는 뜻이다.

주의할 것이 있다. 이 PDF는 정답이 된 그 원고에서 이 책이 직접 조판한 것이다. 그러므로 이 시험은 "원고 → PDF → 추출"의 왕복이 원래대로 돌아오는가를 보는 것이며, 독립된 정답으로 학술지 PDF를 채점한 것이 아니다. 표에 칸막이 선이 그어져 있어서(제1권의 조판 방식) 선 기준에 가장 유리한 경우이다.

## 2.7 선이 없는 표와 열 순서 PDF

학술지의 표는 선이 없는 경우가 많다. 위아래에 가로선 두세 줄만 긋는 "세 줄 표"가 흔하고 세로선은 거의 없다. 그리고 앞 절에서 말한 열 순서로 쓰인 PDF도 있을 수 있다. 이 컨테이너에는 학술지 PDF가 없으므로(실습 2-0에서 접속이 거부되었다) 같은 36개 표를 세 가지로 다시 조판해 시험했다. 도구는 WeasyPrint(HTML을 PDF로 바꿈, 한글 글꼴은 Noto Sans CJK KR을 포함)이다.

- L: 칸막이 선이 있고 행 순서로 쓴 PDF. 제1권 PDF와 같은 모양이다.
- R: 선이 없고 행 순서로 쓴 PDF.
- C: 선이 없고 열 순서로 쓴 PDF. 각 열을 위에서 아래로 쓰고 다음 열로 넘어간다.

36개 표 x 3가지 조판 = 108장이며, 만드는 데 377.0초가 걸렸다(`06-synth-pdf-first.log`). 한 번 만든 PDF는 보관해 두어 다시 돌릴 때는 평가에만 7.6초가 든다.

## 2.8 흩어진 표를 산술로 걸러내고 되짜맞추기

<div class="theory" markdown="1">

#### 이론 배경: 표는 스스로 점검할 수 있는 자료이다

표의 숫자에는 서로의 관계가 들어 있다. 행의 부분을 더하면 합계가 되고, 비율 열은 두 열의 몫에 100을 곱한 값이며, 각 값에는 현실의 범위가 있다. 추출이 열을 흩뜨리면 이 관계가 깨진다. 그러므로 관계가 성립하는지 보는 것이 추출이 맞는지 보는 점검이 된다. 점검은 세 종류이다.

- 행 합 점검: 각 행에서 부분 열의 합이 합계 열과 같은가(허용 오차 안에서).
- 열 합 점검: 합계 행이 위의 행들의 합과 같은가.
- 값 범위 점검: 비율은 0 이상 100 이하, 연도는 현실의 범위처럼 값의 상식 범위를 벗어난 곳이 있는가.

점검이 통과해도 표가 맞다고 증명되지는 않는다. 점검은 틀림을 걸러내는 그물이고, 그물의 눈보다 작은 틀림은 지나간다. 행 합 점검은 한 행 안에서 두 부분 열의 값을 서로 바꾸어도 통과한다(합은 같다). 그 틀림은 다른 점검(비율 열과의 비교)이 있어야 걸린다.

또 하나의 쓸모가 있다. 흩어진 글자열에서 숫자를 다시 짝지을 때, 점검의 조건을 제약으로 쓸 수 있다. "AC + NC = 합계"를 만족하는 세 숫자의 조합을 모두 찾고, 그 조합이 하나로 정해지는지 본다.

**쉬운 예(시연값).** 흩어진 글자열에서 숫자 `10.0, 4.0, 6.0, 20.0, 5.0, 15.0`이 나왔다고 하자. 합계가 되는 조합을 찾으면 `(10.0 = 4.0 + 6.0)`과 `(20.0 = 5.0 + 15.0)`이 나온다. 숫자가 이만큼 적으면 짝이 하나로 정해진다. 숫자가 많아지면 우연히 맞는 조합이 늘어나므로, 조합이 겹치지 않는지(합계 값이 같은 조합이 둘 이상인지)를 같이 센다.

- 제약만으로는 방향(어느 쪽이 AC인가)이 정해지지 않았다. 변화 강도의 사슬은 두 방향까지 줄였고, 하나로 정한 것은 본문에서 읽은 기준값이었다. 4단계의 사슬은 제1권 표의 연도 목록을 이미 알고 쓴 것이어서, 정답을 모르는 표에서는 연도의 순서부터 다시 정해야 한다.

## 2.10 한계와 함정

이 장의 방법이 하지 못하는 일과 만나기 쉬운 함정을 정리한다.

1. **실제 API를 부르지 못했다.** 호출 스크립트는 가짜 서버에서만 실행했다. 필드 이름, 오류 응답의 모양, 한도의 현재 값은 모두 z840에서 확인해야 한다. 가짜 서버가 429를 돌려주는 규칙(0.20초)은 이 책이 정한 값이며 실제 서버의 값이 아니다.
2. **문서끼리 한도가 어긋난다.** OpenAlex의 초당 한도는 도움말 페이지(10, 30, 50)와 인증 페이지(100 초과 시 429)가 다르고, 키 없는 일일 무료 사용량도 두 페이지가 다르다. Crossref의 접근 페이지 표와 2025년 11월 공지도 요청 종류별 값이 다르게 읽힌다. 한도에 가까이 가지 않는 것이 안전하다.
3. **WebFetch는 요약을 돌려준다.** 이 장의 이용 조건 표는 원문과 문구가 다를 수 있다. 서비스를 실제로 쓰기 전에 원문을 직접 읽어야 한다.
4. **DOI 소문자 처리는 가정이다.** DOI가 대소문자를 구별하지 않는다는 점은 이 책이 공식 문서로 확인하지 못했다. 제1권 DB의 관행을 따른 것이다.
5. **상태 열의 대응.** 제1권의 `meta`, `nopdf`가 새 상태의 `abstract`에 해당하는지 확인하지 못했고, `cited`로 옮겼다.
6. **큰따옴표의 함정.** SQLite에서 `"abstract"`는 열 이름으로 읽힌다. 글자 값은 작은따옴표로 쓴다(실습 2-5).
7. **"200 성공"이 PDF를 뜻하지 않는다.** 로그인이나 약관 화면(HTML)이 올 수 있다. 첫 바이트가 `%PDF-`인지 확인한다.
8. **추출은 선이 있는 경우에만 쉽다.** 선 기준은 선이 없으면 한 줄도 못 찾는다. 글자 흐름을 믿는 방법은 열 순서 PDF에서 한 줄도 맞지 않는다. 방법마다 실패하는 조건이 다르므로, 한 방법으로 뽑은 표를 그대로 믿지 말고 점검 함수를 거친다.
9. **점검은 증명이 아니다.** 행 합은 두 부분 열의 값을 서로 바꾼 틀림을 놓친다(실습 2-8). 점검에 통과한 표도 원문과 한 번 대조한다.
10. **이 장은 병합 셀, 회전된 표, 쪽을 넘어가는 표, 스캔 이미지의 표를 시험하지 않았다.** 그런 표에는 이 장의 숫자가 적용되지 않는다.
11. **저작권과 이용 조건.** 논문 PDF를 내려받아 보관하는 일은 출판사와 학술지의 조건에 따른다. 오픈 액세스라는 표시가 재배포를 허락한다는 뜻은 아니다. 이 책은 어느 논문의 이용 조건도 확인하지 않았다(확인 필요).
