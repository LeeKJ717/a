# 10장 로컬 GPU 입문: 드라이버와 CUDA, NumPy에서 CuPy로, 그리고 메모리의 벽

제1권의 계산은 대부분 숫자 몇십 개를 손으로 다시 계산하는 일이었다. 제2권의 뒷부분(11~12장)에서는 같은 계산을 수백만 번 되풀이한다. 부트스트랩이나 순열 검정은 "다시 뽑아 다시 계산하기"를 수만에서 수백만 번 하고, 해안선 모형은 격자의 모든 칸에 같은 식을 적용한다. 이런 일은 컴퓨터의 계산 장치 가운데 같은 연산을 많은 값에 동시에 적용하는 데 맞춰진 그래픽 처리 장치(GPU, graphics processing unit)에 맞는다고들 한다. 이 장은 개인용 컴퓨터에 달린 GPU(이 책이 기준으로 삼은 z840 컴퓨터의 12 GB급 그래픽 메모리)로 넘어가기 전에 알아야 할 것을 세 가지로 나눠 다룬다. 장치를 쓸 수 있게 만드는 일(드라이버와 CUDA), 이미 쓴 파이썬 배열 계산을 장치로 옮기는 일(NumPy에서 CuPy로), 그리고 장치의 메모리가 모자랄 때 하는 일이다.

이 책이 이 장을 쓴 컨테이너에는 GPU가 없다. 그래서 이 장의 모든 실행 결과는 CPU에서 NumPy로 실행한 것이다. GPU에서 잰 시간과 메모리, z840에서의 실행 결과는 "z840 실행 필요"로 비워 두었고, 독자(또는 지은이)가 z840에서 한 번 돌려 채울 수 있게 스크립트(`gpu-bench-v1.py`)를 만들어 두었다. 같은 코드를 `xp = cupy` 또는 `xp = numpy`로 바꿔 쓰는 방식으로 만들었고, 문법 검사와 CPU 경로 실행, 그리고 GPU가 없을 때의 실패 경로 실행까지 이 컨테이너에서 확인했다.

**이 장이 하지 않는 것.**

- 이 장은 GPU에서 실행한 시간이나 메모리를 하나도 싣지 않는다. 해당 칸은 "z840 실행 필요"이다.
- CuPy의 GPU 경로는 실행하지 못했다. 이 컨테이너에서 CuPy를 설치하고 불러오는 것까지는 성공했지만 장치를 쓰는 호출은 모두 실패했다(10.5절). GPU 경로의 코드가 z840에서 한 번에 돈다는 보증은 없다.
- PyTorch는 설치 안내 페이지를 읽었을 뿐 설치하거나 실행하지 않았다. PyTorch를 쓰는 코드는 싣지 않는다.
- NVIDIA 드라이버와 CUDA 도구의 설치는 실행하지 못했다. 공식 안내서에서 읽은 내용만 옮기며, 어느 페이지에서 무엇을 읽었는지 적는다. 확인하지 못한 것은 "확인 필요"이다.
- AMD의 GPU 도구(ROCm)와 애플의 GPU는 다루지 않는다.
- z840의 운영체제, 드라이버 버전, CUDA 버전, GPU 모델을 이 책은 모른다. "12 GB급"은 이 책의 기준 사양(목차안)이며 실제 모델은 확인 필요이다.

**이 장에서 확인한 여섯 가지.**

1. 이 컨테이너에는 GPU가 없다. `nvidia-smi`, `nvcc`, `lspci` 명령이 모두 없고 `/dev/nvidia*`도 없다.
2. GPU가 없는 컴퓨터에서도 `pip install cupy-cuda12x`는 성공하고 `import cupy`도 성공한다. 그러나 장치를 쓰는 호출은 모두 `cudaErrorInsufficientDriver` 예외로 실패한다. 설치가 되었다는 것은 쓸 수 있다는 뜻이 아니다.
3. NumPy로 쓴 코드를 `xp`를 받는 함수로 고쳐 쓰면 NumPy 경로에서 제1권 11장의 값(유전자 다양도 부트스트랩의 0.556, 0.778, 0.889와 노백산-돈화 기상대 거리 82.43 km)이 재현된다. 부트스트랩은 제1권의 2만 번이 아니라 100만 번으로 했다.
4. 점 N개의 N x N 거리 행렬을 계산하는 데 드는 CPU 메모리의 최댓값은 행렬 하나(8N² 바이트)의 약 6.0배였다. N = 8000에서 2.87 GiB가 늘었다. 이 배율로 연장하면 12 GiB 선은 N = 16,400 부근이지만, 이것은 CPU에서 잰 값의 연장이며 GPU에서 잰 값이 아니다.
5. 같은 계산을 나눠서 하면(chunk) 한 번에 하는 것보다 최대 메모리가 크게 줄었다. 부트스트랩 400만 번에서 1044.5 MiB가 90.4 MiB가 되었다.
6. float32로 줄이면 같은 CPU에서 시간이 줄었지만 오차가 생겼다. 약 0.8 m 떨어진 두 점의 거리를 float32로 계산하면 1.093 m가 나왔다(37% 오차). 큰 거리(82 km)에서는 0.000075 km(7.5 cm)의 차이였다.

## 10.2 GPU가 하는 일

<div class="theory" markdown="1">

#### 이론 배경: 왜 배열 계산이 GPU에 맞는다고 하는가

CPU는 코어가 몇 개에서 수십 개이고 코어 하나가 복잡한 일을 빨리 한다. GPU는 코어(실행 단위)가 수천 개이며 하나하나는 단순하다. 그래서 배열의 모든 원소에 똑같은 식을 적용하는 일(원소별 연산)이나 행렬 곱 같은 일은 GPU가 나눠 맡기에 좋고, 원소마다 일이 달라서 갈래가 많은 일은 맞지 않는다고 알려져 있다. 이 서술은 일반적인 설명이며, 이 책은 GPU에서 이를 측정하지 못했다.

이 장에서 기억할 것은 세 가지이다.

1. **전송에는 시간이 든다.** 호스트의 배열을 장치로 보내고(host to device), 결과를 되가져오는 일(device to host)은 계산과 별개로 시간이 든다. 계산이 작으면 전송이 계산보다 오래 걸릴 수 있다. 이 책은 z840에서 전송 시간을 재지 못했다. `gpu-bench-v1.py`는 결과를 호스트로 내리는 시간까지 포함해 재므로, 전송이 포함된 시간이 나온다.
2. **장치 메모리가 작다.** 이 책의 기준은 12 GB급이다. 호스트의 RAM보다 작을 수 있고, 장치 메모리에 들어가지 않는 배열은 쓸 수 없다(10.7절).
3. **float64가 느릴 수 있다.** 일부 GPU는 float64의 처리 속도가 float32보다 훨씬 낮다고 알려져 있으나, 이 책은 z840의 GPU에서 확인하지 못했다. "z840 실행 필요"이다.

## 10.3 환경 구성: 드라이버, CUDA, 파이썬 라이브러리

GPU를 파이썬에서 쓰려면 세 겹이 맞아야 한다. 맨 아래에 NVIDIA 드라이버(운영체제가 GPU를 쓰게 하는 소프트웨어)가 있고, 그 위에 CUDA 도구, 그 위에 파이썬 라이브러리(CuPy나 PyTorch)가 있다. 이 절은 이 책이 공식 페이지에서 읽은 것만 옮긴다.

**NVIDIA의 리눅스 설치 안내서.** 이 책은 CUDA 설치 안내서(NVIDIA, n.d.)의 리눅스판 페이지를 읽었다. 이 책이 읽은 페이지는 CUDA 13.4를 다룬다고 밝혔고, 페이지의 앞 100,000자를 읽었다(전체는 108,833자이며 뒤의 8,833자는 읽지 못했다). 읽은 것은 다음과 같다.

- 필요한 것은 세 가지이다. CUDA를 쓸 수 있는 GPU, gcc 컴파일러와 도구 모음이 있는 지원되는 리눅스, 그리고 CUDA 도구(toolkit).
- CUDA 컴파일러(nvcc)는 호환되는 호스트 컴파일러가 필요하며, x86_64에서 지원 표는 GCC 6.x부터 16.x까지를 적는다. 지원되는 배포판으로 RHEL, AlmaLinux, Rocky, Oracle Linux, SLES, openSUSE Leap, Ubuntu, Debian, Fedora, KylinOS, Azure Linux, Amazon Linux가 열거되고, 표에 확인된 운영체제 판과 기본 GCC 판이 있다.
- GPU가 있는지는 `lspci | grep -i nvidia`로 확인하고 NVIDIA의 CUDA GPU 목록과 견주라고 한다.
- 설치 방법: 배포판 전용 꾸러미(RPM/DEB)를 "가능하면" 쓰라고 권한다. 배포판에 관계없이 되는 자체 설치 파일(runfile)도 있고, 콘다와 pip 휠도 다루는데 pip 휠은 실행용이며 개발 도구를 담지 않는다고 한다.
- 드라이버와 도구의 관계: "CUDA 13.4부터 CUDA 도구와 NVIDIA 드라이버는 따로 설치하고 따로 버전을 매긴다"고 적고, `cuda-toolkit` 메타 꾸러미는 도구만 설치하므로 호환되는 드라이버를 드라이버 설치 안내서에 따라 따로 설치해야 한다고 한다.
- 설치 확인: 이 페이지는 `deviceQuery`와 `bandwidthTest`(cuda-samples 저장소의 예제)를 컴파일해 실행하라고 권한다. 이 책이 읽은 범위에서는 `nvidia-smi`나 `nvcc --version`을 확인 방법으로 적지 않았다. 두 명령이 무엇을 보이는지는 이 책이 공식 문서에서 확인하지 않았으므로 "확인 필요"이며, 이 장의 스크립트는 `nvidia-smi`가 있으면 그 출력을 로그에 남기는 데만 쓴다.

**CuPy의 설치 안내.** CuPy 설치 페이지(CuPy Developers, n.d.-a)에서 읽은 요구 사양과 설치 명령은 아래와 같다.

{{T:CuPy 설치 페이지(stable)가 적은 요구 사양. 이 책이 읽은 페이지 본문에서 옮김}}

| 항목 | 페이지의 서술 |
|---|---|
| GPU | NVIDIA CUDA GPU, 연산 능력(compute capability) 3.0 이상 |

| SciPy(선택) | 1.14부터 1.17까지. GPU의 희소 행렬을 CPU로 복사할 때만 필요 |

설치 명령은 CUDA 12.x에서 `pip install cupy-cuda12x`, CUDA 13.x에서 `pip install cupy-cuda13x`이다. NVIDIA의 CUDA 구성 요소 휠도 함께 설치하려면 `pip install "cupy-cuda12x[ctk]"`처럼 `[ctk]`를 붙인다. 콘다에서는 `conda install -c conda-forge cupy`가 미리 만든 이진 파일과 CUDA 실행 라이브러리를 함께 설치한다고 한다. 같은 페이지는 CuPy 꾸러미(`cupy` 또는 `cupy-cudaXX`)는 하나만 설치하라고 경고하며(`pip freeze | grep cupy`로 확인), 서로 충돌한다고 적는다.

**PyTorch의 설치 안내.** PyTorch의 "로컬에 설치" 페이지(PyTorch, n.d.)는 설치 환경을 고르는 선택기가 있는 동적 페이지여서, 이 책이 읽은 본문에는 명령이 하나만 있었다. 읽은 것은 다음과 같다.

- "최신 안정판 PyTorch는 파이썬 3.10 이상이 필요하다."
- 리눅스는 glibc 2.28 이상인 배포판에서 지원한다(Ubuntu는 20.04 이상으로 적혔으나 페이지가 그 판의 지원 종료를 언급했다). 윈도우는 Windows 7 이상이며 10 이상을 권장한다.
- GPU는 "권장하지만 필수는 아니다."
- 계산 플랫폼 후보로 CUDA 11.8, 12.6, 12.8, ROCm 6.3, CPU가 열거되었고 안정판은 2.7.0으로 표기되었다. **이 책의 날짜(2026-10-26)에 비해 오래된 표기로 보이므로, 이 책은 이 목록을 현행으로 믿지 않는다.** 현행 지원 목록은 선택기에서 확인해야 한다(확인 필요).
- 본문에 있던 설치 명령은 리눅스, pip, CUDA 11.8용 한 줄이었다: `pip3 install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu118`.
- 설치 확인: `import torch`를 불러 `torch.cuda.is_available()`을 부르라고 안내한다. 이 책이 읽은 본문은 기대 반환값을 적지 않았다.

이 책은 PyTorch를 설치하지도 실행하지도 않았다. 이 장의 코드는 CuPy 경로만 만들었다. 이유는 두 가지이다. CuPy 설치 페이지가 NumPy와 SciPy에 호환되는 API를 제공한다고 밝히므로(CuPy Developers, n.d.-a) 제1권의 NumPy 코드를 옮기기 쉬울 것이라 보았고, 이 컨테이너에서 CuPy는 설치와 이름 확인까지 해 볼 수 있었다.

**이 책이 확인하지 못한 것.**

- z840의 운영체제, 드라이버, CUDA 버전, GPU 모델. 이 장의 `gpu-bench-v1.py`가 z840에서 이를 로그에 남기도록 해 두었다.
- 윈도우에서의 설치 절차. CuPy 페이지는 "Windows Server 2016"을 시험 환경으로 적을 뿐이고 일반 윈도우 10·11의 지원 여부를 이 책이 읽은 본문에서는 확인하지 못했다.
- NVIDIA 드라이버를 내려받는 곳과 설치 절차(드라이버 설치 안내서를 읽지 않음).

## 10.4 GPU가 있는가: 확인 명령

<div class="method" markdown="1">

## 10.5 CuPy를 설치하면 GPU가 없어도 설치는 된다

<div class="method" markdown="1">

**입력.** 새 가상환경. 인터넷(PyPI).

## 10.6 NumPy에서 CuPy로: 같은 코드를 xp로 바꿔 쓰기

<div class="theory" markdown="1">

#### 이론 배경: xp 관례와 CuPy가 보증하는 것

CuPy는 NumPy와 같은 이름의 함수를 GPU 배열에 대해 제공한다(CuPy Developers, n.d.-a). CuPy 기초 문서(CuPy Developers, n.d.-c)는 다음을 설명한다.

- `cupy.asarray(x)`는 NumPy 배열이나 리스트를 현재 장치로 옮긴다. "가능하면 입력을 복사하지 않는다"고 하여, 이미 현재 장치에 있는 배열을 주면 같은 객체를 돌려준다.
- `cupy.asnumpy(x)`와 `x.get()`은 장치 배열을 호스트의 NumPy 배열로 내린다.
- NumPy 배열과 CuPy 배열을 섞어 더하면 `TypeError`가 난다. 한쪽을 먼저 옮겨야 한다.
- `cupy.get_array_module(x)`는 인자 중 하나라도 GPU에 있으면 `cupy`를, 아니면 `numpy`를 돌려준다. 문서는 이를 쓴 예에서 결과 이름을 `xp`로 쓰고 "`xp`는 커뮤니티의 표준 용법"이라고 주석에 적는다.
- CuPy는 "현재 장치"라는 개념을 쓴다. 장치를 바꾸려면 `with cp.cuda.Device(1):` 문맥을 쓴다.

이 장은 한 걸음 더 간다. 계산 함수가 `xp`를 첫 인자로 받게 하고, 백엔드를 고르는 곳을 한 곳(`choose_xp`)으로 모으며, 장치에서 호스트로 내리는 곳을 한 함수(`to_host`)로 표시한다. 이렇게 하면 같은 계산 함수를 NumPy로도 CuPy로도 부를 수 있고, 어디서 전송이 일어나는지 코드에서 한눈에 보인다.

**난수는 같지 않다.** NumPy의 난수와 CuPy의 난수는 같은 시드를 줘도 같은 열을 낸다고 이 책이 읽은 문서에 적혀 있지 않다. 이 책은 같다고 가정하지 않는다. 그러므로 GPU 결과와 CPU 결과의 비교는 "글자 하나까지 같다"가 아니라 "모의의 오차 범위 안에서 같다"로 해야 한다. 이 장의 점검이 부트스트랩의 분위수를 비교하는 이유이다.

</div>

이 장의 `xp-demo-v1.py`는 제1권 11장의 두 계산을 `xp` 방식으로 다시 쓴 것이다. 하나는 계산 11-4의 유전자 다양도 부트스트랩이고, 다른 하나는 계산 11-13의 하버사인(대원) 거리이다. 제1권은 부트스트랩을 반복문으로 2만 번 돌렸지만 여기서는 배열 연산 하나로 한 조각(chunk)의 모든 반복을 한꺼번에 계산한다. 핵심 부분은 아래와 같다.

```
def choose_xp(name):
    """name: 'numpy', 'cupy', 'auto'. cupy가 없거나 GPU가 없으면 auto는 numpy로 내려간다."""
    if name in ('cupy', 'auto'):
        try:
            import cupy as cp
            cp.cuda.runtime.getDeviceCount()          # 드라이버가 없으면 여기서 예외
            return cp
        except Exception as e:
            if name == 'cupy':
                raise SystemExit('cupy 경로를 쓸 수 없다: %s: %s' % (type(e).__name__, str(e).splitlines()[0]))
            print('[알림] cupy를 쓸 수 없어 numpy로 내려간다 (%s)' % type(e).__name__, file=sys.stderr)
    return np
def to_host(xp, a):
    return xp.asnumpy(a) if xp is not np else a
def boot_h(xp, counts, B, seed, chunk):
    """같은 빈도에서 n명을 복원추출하는 부트스트랩으로 Nei 다양도 H를 B번 구한다."""
    counts = list(counts); k = len(counts); n = sum(counts)
    labels = xp.asarray(np.repeat(np.arange(k), counts))        # 사람 n명의 하플로그룹 번호
    ks = xp.arange(k)
    rng = xp.random.default_rng(seed)
    out = []
    for start in range(0, B, chunk):
        m = min(chunk, B - start)
        idx = rng.integers(0, n, size=(m, n))                   # (m, n) 복원추출 번호
        cat = labels[idx]                                       # (m, n)
        c = (cat[:, :, None] == ks[None, None, :]).sum(axis=1)  # (m, k) 각 형의 수
        p = c / n
        out.append(n / (n - 1) * (1.0 - (p * p).sum(axis=1)))
    return xp.concatenate(out)
def haversine_matrix(xp, lon, lat, R=6371.0088, dtype=None):
    lon = xp.asarray(lon, dtype=dtype); lat = xp.asarray(lat, dtype=dtype)
    la = xp.radians(lat); lo = xp.radians(lon)
    dla = la[:, None] - la[None, :]
    dlo = lo[:, None] - lo[None, :]
    a = xp.sin(dla / 2) ** 2 + xp.cos(la)[:, None] * xp.cos(la)[None, :] * xp.sin(dlo / 2) ** 2
    return 2 * R * xp.arcsin(xp.sqrt(a))
```

코드에서 볼 것은 세 가지이다. 첫째, 함수 안의 모든 배열 연산이 `xp.`로 시작한다. 둘째, 배열을 만들어 장치로 보내는 곳(`xp.asarray`)이 함수의 맨 앞에 한 번 있다. 셋째, 반복 횟수 B가 아무리 커도 한 번에 `chunk`개만 메모리에 올리므로 메모리 크기가 B에 비례하지 않는다(10.7절).

이 방식은 다음을 가정한다. (가) NumPy와 CuPy가 같은 이름의 함수를 같은 뜻으로 제공한다(`xp.sin`, `xp.cos`, `xp.arcsin`, `xp.radians`, `xp.sqrt`, `xp.concatenate`, `xp.percentile`, `xp.random.default_rng(seed).integers` 등). 이 책은 이 이름들이 CuPy 14.2.0에 있음을 확인했지만(실습 10-2) 그 동작을 GPU에서 확인하지는 못했다. `.sum(axis=1)`, `.mean()`, 인덱싱, `==` 같은 배열 자체의 연산은 이름 확인을 하지 않았다. (나) 인덱싱 `labels[idx]`와 비교 `cat[:, :, None] == ks[None, None, :]`이 CuPy에서도 같은 뜻이다. 이 책은 확인하지 못했다. "z840 실행 필요"이다.

## 10.7 메모리의 벽

<div class="theory" markdown="1">

#### 이론 배경: 배열의 크기와 임시 배열

배열 하나가 차지하는 메모리는 원소 수 × 원소 하나의 바이트이다. float64는 8바이트, float32는 4바이트, 불리언(참/거짓)은 1바이트로 저장된다(NumPy의 일반적인 방식). 점 N개의 N x N 거리 행렬은 float64에서 8N² 바이트이다. N = 8000이면 488.3 MiB이고 N = 16000이면 1953.1 MiB이다.

그러나 계산에 필요한 메모리는 결과 배열 하나보다 훨씬 크다. `a + b * c` 같은 식은 `b * c`의 중간 결과를 임시 배열로 만든 뒤 `a`와 더한다. 식이 복잡할수록 같은 크기의 임시 배열이 여러 개 동시에 살아 있다. 이 장의 하버사인 계산은 위도 차, 경도 차, 사인 제곱, 코사인 곱 등 N x N 임시 배열을 여러 개 만든다.

**CuPy의 메모리 풀.** CuPy 문서(CuPy Developers, n.d.-b)는 CuPy가 기본으로 "메모리 풀을 쓴다"고 설명한다. 배열이 범위를 벗어나면 장치 메모리는 풀에 "남겨져 다시 쓰이도록 보관"되며 운영체제에 곧바로 돌려지지 않는다. 그래서 배열을 지워도 `nvidia-smi` 같은 도구에서 메모리 사용량이 줄지 않은 것처럼 보일 수 있다고 문서는 "예상된 동작"이라고 적는다. 문서가 보인 풀의 도구는 다음과 같다.

- `mempool = cupy.get_default_memory_pool()`로 기본 풀을 얻고, `mempool.used_bytes()`와 `mempool.total_bytes()`로 쓰는 중인 바이트와 확보한 바이트를 본다.
- `mempool.free_all_blocks()`는 쓰지 않는 블록을 모두 돌려준다.
- 환경 변수 `CUPY_GPU_MEMORY_LIMIT`로 쓸 수 있는 장치 메모리를 제한할 수 있고, 코드에서는 `with cupy.cuda.Device(0): mempool.set_limit(size=1024**3)`처럼 장치별로 제한한다(문서 예시는 1 GiB). 문서는 CUDA가 풀 밖에서 확보하는 메모리는 이 제한에 세어지지 않는다고 덧붙인다.
- 문서에는 HMM이나 ATS를 지원하는 시스템(NVIDIA Grace Hopper 같은)에서 호스트와 장치가 메모리를 공유하는 실험적 방식("unified memory")도 있으나, 이 책의 기준 사양이 그에 해당하는지 알 수 없어 다루지 않는다.

이 책의 `gpu-bench-v1.py`는 풀이 확보한 바이트와 쓰는 중인 바이트, 장치 전체와 남은 바이트(`memGetInfo`)를 매 항목마다 기록한다. 문서가 풀이 메모리를 쥐고 있다고 한 것에 따라, 항목 사이에 `free_all_blocks()`를 불러 이전 항목의 영향을 지운다.

**해결 방법: 쪼개서 계산한다.** 메모리가 모자라면 결과를 한 번에 만들지 않고 조각(chunk)으로 나눠 조각마다 계산하고 줄여서(예: 최댓값, 합, 분위수의 기초가 되는 값) 쌓는다. 이 장의 `boot_h`가 그렇게 한다.

## 10.11 한계와 함정

**설치는 되는데 쓸 수 없는 경우.** 실습 10-2에서 보았듯 GPU 없이도 CuPy의 설치와 `import`는 성공하고 첫 장치 호출에서 실패한다. 설치 직후에 장치를 한 번 불러 확인하는 코드(`cupy.cuda.runtime.getDeviceCount()`)를 넣는다. `choose_xp`가 이 일을 한다.

**두 개의 CuPy를 깔지 않는다.** CuPy 설치 페이지는 `cupy`와 `cupy-cudaXX` 가운데 하나만 설치하라고 경고한다. 다른 CUDA 버전용을 번갈아 시험하면 충돌할 수 있으므로, 가상환경을 새로 만든다(0장).

**NumPy의 버전.** CuPy 문서의 범위는 NumPy 2.0~2.4이다. 이 컨테이너에서 `pip`가 기본으로 고른 NumPy는 2.5.4였고 CuPy는 불러졌다. 범위 안(2.4.6)에서도 같은 스크립트가 같은 값을 냈다. 이 책은 GPU 경로에서 두 버전의 차이를 확인하지 못했다.

**난수가 다르다.** NumPy와 CuPy가 같은 시드에서 같은 난수열을 낸다고 가정하지 않는다. GPU와 CPU의 부트스트랩 결과를 글자 하나까지 맞추려 하지 말고, 모의 오차(반복 횟수의 제곱근에 반비례하는 크기) 안에서 같은지를 본다. 이 장의 계산은 H가 17개의 값만 가져서 분위수가 쉽게 같아지지만, 연속 값에서는 아니다.

**GPU 계산은 비동기이다.** CuPy에서 계산을 시킨 뒤 곧바로 시계를 읽으면 계산이 끝나기 전의 시간이 나올 수 있다. `gpu-bench-v1.py`는 `Device.synchronize()`를 부른 뒤에 시계를 읽는다. 이 동작은 이 책이 GPU에서 확인하지 못했다.

**첫 실행은 느리다.** 워밍업을 따로 적는다. 이 컨테이너의 CPU에서도 워밍업이 중앙값보다 큰 경우가 많았다.

**메모리 풀이 쥐고 있다.** CuPy 문서가 설명하듯 배열을 지워도 `nvidia-smi`의 사용량이 줄지 않을 수 있다. `free_all_blocks()`를 부르거나 새 프로세스를 띄운다. 풀이 확보한 바이트와 쓰는 중인 바이트는 다른 값이다.

**메모리는 결과보다 크다.** 임시 배열 때문에 필요한 메모리는 결과 배열의 몇 배이다. 이 컨테이너의 하버사인 계산에서 CPU 메모리는 행렬 하나의 약 6배였다. 장치에서는 다를 수 있다.

**float32.** 빠르고 작지만 가까운 점의 거리에서 오차가 컸다(실습 10-6). 계산의 허용 오차를 먼저 정한다.

**한 번의 시간으로 판단하지 않는다.** 같은 스크립트의 두 번의 실행에서 N = 8000, float64가 6.25초와 3.48초로 달랐다. z840에서도 여러 번 실행해 범위를 본다.

**작은 계산은 GPU가 이기지 못할 수 있다.** 전송과 준비 비용이 계산보다 클 수 있다고 알려져 있다. 이 책은 z840에서 이를 확인하지 못했다. 이 장의 `gpu-bench-v1.py`는 B = 100,000과 N = 1000 같은 작은 항목도 포함해 이 현상이 z840에서 보이는지 볼 수 있게 했다.

**더 읽을 책.** 이 책이 읽은 GPU 프로그래밍 교재는 없다. 그러므로 교재 목록을 두지 않는다. 읽은 문서는 참고문헌에 있다.
